## 一、这个系统能做什么

这个系统不是"给运维加一个聊天框"，而是把运维工作中**四类高频、高风险、需要留痕**的任务，做成了可执行、可审批、可回溯的闭环。

下面按"你会怎么用它"来写，而不是按功能菜单来写。

### 场景 A：凌晨告警，需要快速定位根因

**你会输入什么**

一句话就够了，比如：

> web-01 磁盘满了，Nginx 报 No space left on device

也可以直接点界面左侧的预置场景（磁盘写满 / Java OOM / 慢查询暴涨 / Redis 下线 / 网关 502），或者粘贴一段日志。

**系统实际做了什么**

它不会直接编一个答案给你，而是先**自己去取证**。这个过程是可见的——界面上会逐个亮起工具调用卡片：

```
1) list_hosts()               → 确认 5 台受管主机及其角色
2) query_metrics(web-01, disk) → 拿到磁盘使用率时序，看到 96% 且仍在上涨
3) get_alerts(web-01)          → 拿到该机未恢复告警，含 inode 告警
4) query_logs(web-01, nginx, "space") → 捞到 No space left on device 原文
5) check_services(web-01)      → 发现 filebeat = failed
6) top_processes(web-01, mem)  → 排除进程异常占用
```

拿齐证据之后，才生成报告。

**你会拿到什么**

固定六段结构，每一段都要求引用具体数值或日志原文：

| 段落 | 内容 | 举例 |
|---|---|---|
| 结论摘要 | 一两句话定性 | 磁盘空间（含 inode）耗尽导致 Nginx 无法写日志与 PID 文件 |
| 证据链 | 每条结论对应哪次工具返回的哪个数值 | `disk` 使用率 96%；`inode` 使用率 98% |
| 可能原因 | **按可能性排序**，并标注"为什么不是别的原因" | 高：日志未轮转；中：filebeat 中断导致上游堆积 |
| 排查步骤 | 可直接照着敲的命令 | `du -sh /var/log/* \| sort -h` |
| 修复建议 | 短期止血 + 长期治理分开写 | 短期清日志、长期配 logrotate |
| 还需补充的信息 | 诚实说明哪些结论因为缺数据而无法确认 | 缺少 /data 分区历史增长曲线 |

**为什么"证据链"是硬要求**

因为运维最怕的不是没答案，而是**一个看起来很合理但错的答案**。这个系统在设计上禁止无依据输出——提示词里明确要求"每条结论必须引用工具返回的数值或日志原文"，同时演示引擎（无 Key 时使用的本地推理）也是按证据拼装报告的，不存在凭空生成。

### 场景 B：同事发来一个部署脚本，让你 review

**你会输入什么**

把脚本贴进「脚本校错」页，或者点「载入示例」看内置的 `samples/risky-deploy.sh`（一份故意写得很危险的脚本）。

**系统实际做了什么**

三段式，且顺序不能反：

1. **本地规则引擎先跑一遍**（毫秒级，20 类风险规则）。这一步不依赖网络、结果确定。
2. **AI 再审一遍补语义**。规则只能抓模式，抓不到"这个业务逻辑有问题"；AI 输出约定 JSON Schema：`{summary, overall_risk, issues[{severity, line, risk, suggestion, patch}]}`。
3. **每一条修复都先给你看 diff**。

示例脚本（`samples/risky-deploy.sh`）在第一段就会报出 14 项：

| 级别 | 命中项 |
|---|---|
| critical | `rm -rf` 作用于未加引号的变量 · `curl \| bash` 下载即执行 · 批量修改系统账号密码 |
| high | 缺少 `set -euo pipefail` · 明文机密写入 `DB_PASS` · 数据库密码走命令行参数 · 强制 `kill -9` · 对根路径/通配路径强制删除 |
| medium | 缺少备份或回滚入口 · `cd` 后未校验是否成功 · `\|\| true` 吞掉失败 |
| low | 缺少 `trap` 清理 · 固定 `sleep` 等待服务就绪 · 用 `$?` 判断上一条命令 |

**你会拿到什么**

风险清单 + 逐条 diff。**点「确认应用」之前，原始脚本一个字都不会变。**

补丁不是"让 AI 重写整个文件"，而是机器可执行的最小指令：

```js
{ type: 'replace', find: 'rm -rf $TARGET', replace: 'rm -rf "${TARGET:?TARGET 未设置}"' }
{ type: 'insert',  anchor: 0, position: 'after', text: '\nset -euo pipefail' }
```

这样做的原因很实际：让模型自由改写整份文件，它很容易顺手改掉无关逻辑，而你在 diff 里看不出来。

### 场景 C：真的要动生产了——清理 7 天前日志

这是整个系统最需要克制的地方。**从"我想要"到"真的执行"，中间有四道卡口，一道都不能跳。**

```
意图 → 1)生成草稿 → 2)静态门禁 → 3)他人审批 → 4)隔离执行
```

**① 生成草稿**

输入"清理 7 天前的过期日志"，命中 `log-cleanup` 模板，产出 52 行脚本。生成物**天然带三层安全带**：

```bash
set -euo pipefail                      # 出错即停，未定义变量即报错，管道失败即失败
trap 'echo "[trap] 脚本中断退出"; exit 2' EXIT   # 中断也有兜底
APPLY="${APPLY:-0}"                    # 默认 dry-run
if [ "${1:-}" = "--apply" ]; then APPLY="1"; fi
```

不加 `--apply`，脚本只打印"将要删什么"，不动手。这是"默认安全"（secure by default），而不是"记得加 --dry-run"。

**② 静态门禁**

生成完立刻评估，两级判定：

| 级别 | 后果 | 触发示例 |
|---|---|---|
| `blocked` | **直接拒绝，审批也救不回来** | `rm -rf`、`mkfs`、`dd`、`shutdown/reboot`、`chpasswd`、`curl \| bash`、`chmod 777`、写块设备、`DROP TABLE`、无 `WHERE` 的 `DELETE`、`userdel`、`systemctl stop/disable/mask` |
| `needs_approval` | 可以入库，但必须人工点头 | `find -delete`、`systemctl restart`、`kill`、`cp -f`/`mv -f` |

界面上会直接看到红色「门禁拒绝」+ 具体原因，而不是提交之后才吃一个 403。

**③ 他人审批**

提交后进入审批队列，状态 `pending`。

关键规则：**提交人不能批准自己提交的变更**。同一个人点「批准」按钮是灰的，鼠标悬停提示"不能批准自己提交的变更，请切换操作人"。要演示完整流程，得在顶栏换一个身份。

**④ 隔离执行**

批准后，点「在隔离环境执行」。执行前会**重新跑一遍门禁**——防止脚本在审批之后被人偷偷改过（TOCTOU 问题）。

默认 `mock` 模式，逐行回显"会发生什么"，并明确标注「模拟执行·不产生真实副作用」。真跑用 `docker` 模式：

```bash
docker run --rm -i \
  --network=none \
  --memory=256m --cpus=0.5 --pids-limit=64 \
  -v <workspace>:/work:ro -w /work \
  alpine:3.19 sh -s
```

无网络、限内存、限 CPU、限进程数、工作区只读挂载、一次性容器。

### 场景 D：交接班 / 事后追溯——谁在什么时候批了什么

点右上角「审计日志」，抽屉里是 append-only 的 JSONL 记录，每条带：

```
时间 · 事件类型 · 操作人 · 角色 · 入参 · 结果 · 耗时
```

覆盖的事件类型：`user_message`、`tool_call`、`tool_denied`、`approval_submit`、`approval_decision`、`exec_finished`、`gate_check`、`agent_done`、`llm_error`。

可以按类型筛选，也可以 `GET /api/audit/export` 导出全量 JSON。

### 场景 E：权限分层——新人只能看，值班长才能批

顶栏可切换四种身份，按钮会实时置灰/恢复：

| 角色 | 能做什么 | 现实对应 |
|---|---|---|
| `viewer` 观察员 | 看分析、调只读工具、脚本体检、看审计 | 一线 / 新人 |
| `operator` 运维执行 | + 生成脚本、提交审批 | 一线运维 |
| `approver` 变更审批人 | + 批准/驳回、隔离执行 | 值班负责人 |
| `admin` 管理员 | 全部（演示用） | 平台管理员 |

**注意：前端置灰只是体验，真正的边界在服务端。** 用 curl 带着 `x-ops-role: viewer` 头直接请求审批接口，一样是 403。

### 能力小结（一张表看完）

| 能力 | 输入 | 输出 | 是否需要人确认 | 是否有副作用 |
|---|---|---|---|---|
| 故障分析 | 一句话 / 日志 / 告警 | 带证据链的六段式报告 | 否（只读） | 无 |
| 脚本校错 | Shell 脚本 | 风险清单 + 逐条 diff | **是**（diff 确认） | 无（只改编辑器内容） |
| 工具取证 | 工具名 + 参数 | 指标 / 日志 / 服务状态等 | 否（只读） | 无 |
| 脚本生成 | 变更意图 | 带安全骨架的脚本草稿 | 否（只生成） | 无 |
| 变更审批 | 脚本 + 意图 | 审批单（状态机） | **是**（他人批准） | 无 |
| 隔离执行 | 审批单 ID | stdout / stderr / 退出码 | 已批准才行 | 有（可控范围内） |
| 审计追溯 | 时间 / 类型 | JSONL 记录 | 否（只读） | 无 |

## 二、它刻意不做什么

技术文档里写清边界，比写清功能更重要。以下都是**设计上的主动选择**，不是没做完：

| 不做 | 原因 |
|---|---|
| **不直接对生产主机执行命令** | 默认 `mock` 模拟执行。要真跑必须显式切 `docker`，而且只能跑"别人提交、别人批准、且过了门禁"的那份脚本 |
| **不把模型权重下载到本地** | 模型始终通过 API 调用。本项目部署的是**执行环境、工具和数据的自托管**，不是大模型私有化。这两件事在简历和汇报里必须分开说 |
| **不替代监控/CMDB/堡垒机** | 它是编排层：取证数据可以来自 Prometheus / Zabbix / 云监控，执行最终应落到堡垒机 + 受限账号。现在用 `sandbox/` 的确定性模拟数据，是为了结果可复现、可测试 |
| **不让模型自由改写整份脚本** | 只接受结构化 patch，前端逐字定位替换。原因是可审查性——diff 里出现无关改动你根本看不出来 |
| **不把审批权交给模型** | 审批是人的决策。模型可以生成、可以评估风险，但不能批准自己的产出 |
| **不让工具报错终止会话** | 工具失败会被回灌给模型，让它自己换路子。这是真实 Agent 与"一次性的 RPC 调用"的本质区别 |

## 三、整体架构与数据流

### 3.1 分层

```
┌─ 浏览器   原生 HTML/CSS/JS，无构建步骤
│    故障分析 · 脚本校错 · 工具沙箱 · 自动化运维 · 审计抽屉
└──────────── HTTP + SSE  ─────────────────────────────────
┌─ 路由层   routes/api.js
│    actorOf() 取身份 · requirePermission 声明式守卫 · asyncHandler 包异步
├─ 编排层   agent/loop.js
│    按角色过滤工具 · 推理调用回灌多轮 · 达上限后强制收敛
├─ 能力层
│    tools.js          9 个只读工具 + 路径白名单 + 结果截断
│    write-tools.js    4 个写操作工具（执行只收 approval_id）
│    scriptgen.js      6 个模板，安全骨架 + 默认 dry-run
│    executor.js       静态门禁 + 三后端执行（mock / docker / local）
│    approval.js       审批状态机 + 职责分离 + 持久化
├─ 支撑层
│    llm/provider.js    双协议 + 兼容性降级重试
│    llm/mock.js        演示推理引擎（无 Key 跑通全链路）
│    lib/sse.js         手写 SSE 解析（缓冲 + 分包切帧）
│    lib/shell-lint.js  20 类 Shell 风险规则
│    lib/errors.js      结构化错误（code / retryable / hint）
│    security/rbac.js   角色权限矩阵
│    audit.js           append-only JSONL（同步写）
└─ 数据层   sandbox/（5 台模拟主机 · 确定性伪随机，可复现）
           data/（audit.log · approvals.json）
```

### 3.2 三条主要数据流

**流 1：SSE 对话（阶段 1/2）**

```
浏览器 POST /api/chat
   → 路由层创建/复用会话，取 actor/role
   → loop.runAgent()
       ├─ turn 1: 模型返回 tool_calls
       ├─ 逐个执行工具 → emit(tool_start) / emit(tool_result)
       ├─ 结果压成 role=tool 消息入会话
       ├─ turn 2: 模型基于证据生成报告 → emit(delta) 流式吐字
       └─ emit(done)
   → SSE 帧逐条 flush 到浏览器
   → 前端按 data.type 分发：delta 追加文本 / tool_start 建卡片 / tool_result 更新卡片
```

**流 2：审批执行（阶段 4）**

```
前端提交脚本 → POST /api/approvals
   → gateScript(script)          ← 门禁，blocked 直接 403，不入库
   → submitApproval()            ← 写 approvals.json，状态 pending，记审计
   → 换身份 → POST /api/approvals/:id/decision
   → decideApproval()            ← 校验 pending + 提交人≠审批人 + 权限，状态 → approved
   → POST /api/approvals/:id/execute
   → 重新 gateScript()            ← 二次门禁，防审批后被改
   → executeScript({mode})       ← mock/docker/local
   → markExecuted()              ← 状态 → executed，记审计
```

**流 3：只读工具直连（阶段 3，用于单独验证）**

```
前端选工具 + 填参数 → POST /api/tools/invoke
   → 若工具有 requiredPermission → requirePermission()
   → runTool(name, args)
   → 记 tool_call_manual 审计
```

## 四、核心机制拆解

这一节讲"它是怎么做到的"，按重要性排序。

### 4.1 Agent 循环：为什么必须多轮

**单轮调用的死穴**

如果只是"把用户问题 + 工具清单发给模型，拿回复"，模型会做一件很危险的事：**编造工具结果**。因为它没有被喂过真实数据，只能靠语言先验猜一个"听起来对"的答案。

所以必须有第二轮：

```
turn 1  → 模型说"我要调 query_metrics(web-01, disk)"
        → 系统真的去查，把结果作为 role=tool 消息塞回会话
turn 2  → 模型现在"看见"了 96% 这个数字，才敢下结论
```

这就是 function calling 的本质：**不是让模型执行，而是让模型表达意图，由系统执行，再把事实回灌。**

**四个必须处理的工程问题**

| 问题 | 不处理的后果 | 本项目的做法 |
|---|---|---|
| 无限循环 | 模型反复取证，费用爆炸，请求挂死 | `AGENT_MAX_TURNS=6`（默认）硬上限 |
| 到上限后沉默 | 用户等了 6 轮拿到空回复 | 第 6 轮强制注入收敛指令 `FORCE_CONCLUDE_HINT`，且 `tools: []` 让它只能说话不能调工具 |
| 单个工具结果太大 | 一次返回 50MB 日志 → 上下文爆掉 | `compactToolResult()` 截断到 6000 字符；`previewOf()` 给前端只留 800 字符 / 最后 5 行 |
| 客户端断开 | 后台还在烧 token | `AbortSignal` 贯穿每一轮，`checkAbort()` 在每个循环点检查 |

**权限拒绝也要继续对话**

这是容易被忽略但很关键的一点。当模型调用了当前角色没有权限的工具时，代码不是抛错终止，而是：

```js
toolResult = {
  ok: false,
  error: '权限不足：调用工具 approve_change 需要 approval:decide',
  hint: '当前角色为 viewer，请换用只读工具或联系审批人',
  code: 'FORBIDDEN',
};
```

然后这条结果照常作为 `role=tool` 消息回灌。模型会理解"这条路走不通"，改用别的办法，或者直接告诉用户"这需要审批人操作"。

**为什么这比直接报错好**：报错会让整个对话死掉，用户得重新开始；回灌则让 Agent 表现出"知道自己的边界"，体验上像一个懂规矩的同事，而不是一个崩掉的程序。

### 4.2 SSE 流式：分包才是真问题

浏览器端用的是 `fetch` + `ReadableStream`，因为原生 `EventSource` 不支持 POST 和自定义请求头。

手写解析器 `server/lib/sse.js` 要处理的核心问题是：**TCP 分包边界和 SSE 帧边界不对齐。**

```
服务端发出：  "data: {\"type\":\"delta\",\"text\":\"你好\"}\n\n"
网络实际到达："data: {\"type\":\"del" + "ta\",\"text\":\"你好\"}\n\n"
                         ↑ 第一包到这里断了
```

如果按行读，第一包就是一个不完整的 JSON，`JSON.parse` 直接炸。正确做法是**缓冲 + 按 `\n\n` 切分**：

```js
buffer += chunk;
const frames = buffer.split('\n\n');
buffer = frames.pop();          // 最后一段可能不完整，留到下一包
for (const frame of frames) {   // 只处理确定完整的帧
  // 解析 data: 行
}
```

另外还要 normalize `\r\n`（Windows 代理会改行尾），以及处理 `[DONE]` 结束信号。

**服务端踩过的一个坑**

Express 4 + Node 16+ 下，`req.on('close')` 在**请求体读完**时就触发了，不是客户端断开时。早期用它做取消信号，结果推理在 276ms 就被中止。正确做法是监听 `res.on('close')`：

```js
res.on('close', () => { if (!res.writableEnded) controller.abort(); });
```

### 4.3 双协议接入与降级重试

同一套上层逻辑，要能跑在两种 OpenAI 协议上：

| 差异点 | Chat Completions | Responses API |
|---|---|---|
| 工具格式 | `{type:'function', function:{name, description, parameters}}` | `{type:'function', name, description, parameters}`（扁平） |
| 会话状态 | 客户端自管 `messages` 数组 | 可用 `previous_response_id` 服务端托管 |
| 工具结果回灌 | `role: 'tool'` 消息 | `function_call_output` item |
| 系统提示 | `role: 'system'` | `instructions` 字段 |

`provider.js` 用 `toChatTools()` / `toResponsesTools()` / `toResponsesInput()` 三个转换函数把差异吃掉，对外统一输出：

```js
{ content, toolCalls: [{id, name, arguments}], finishReason, usage, responseId }
```

上层 `loop.js` 完全不关心底层是哪种协议。

**降级重试（真实世界的必需品）**

很多 OpenAI 兼容中转站不支持 `parallel_tool_calls`、`stream_options`、`tool_choice`、`temperature`。一上来就 400。

所以请求分两档构造：

```js
buildBody({ variant: 'full' })     // 带全部能力字段
buildBody({ variant: 'minimal' })  // 剔除兼容性差的字段
```

`400 / 404 / 422` 时自动用 minimal 重试一次。**这一条把"换个中转站就跑不起来"的失败率降了一大截**，是纯工程经验，不是文档里能查到的。

### 4.4 会话状态：为什么自己管而不用 previous_response_id

`session.js` 里同时保留了两种能力，但默认走客户端自管。三条理由：

1. **可审计**——每轮输入输出都在自己手里，能落盘、能重放、能做敏感信息过滤；托管在服务端你就只剩一个 ID。
2. **可移植**——换成任何 OpenAI 兼容服务都不受影响。
3. **可控**——能做历史裁剪，防止上下文越滚越大导致费用失控。

**历史裁剪的坑：tool 消息不能孤立**

直接把前面几条消息砍掉，很容易留下一条孤立的 `role: 'tool'` 消息。而 API 规定 tool 消息必须紧跟在它对应的 `assistant.tool_calls` 之后，否则直接报错。

所以裁剪逻辑是：

```js
let keep = rest.slice(-(max - head.length));
while (keep.length && keep[0].role === 'tool') {
  keep = keep.slice(1);   // 如果切口落在 tool 上，往前多砍一条
}
```

同时保留 system 提示（它不在 messages 里，是每轮拼接的），6 小时 TTL 回收。

### 4.5 只读工具层：安全红线写在代码里

9 个只读工具：

| 工具 | 作用 | 关键约束 |
|---|---|---|
| `list_hosts` | 主机清单（角色/IP/环境） | 可按 env、role 过滤 |
| `query_metrics` | 指标时序（cpu/mem/disk/inode/io_wait/…） | 采样点数上限 60 |
| `get_alerts` | 未恢复告警 | 可按主机、严重级别过滤 |
| `query_logs` | 日志检索 | 只能读沙箱内样本，source 错时返回可用列表 |
| `check_services` | 服务状态（systemctl status 只读视图） | 只读 |
| `top_processes` | 进程 TOP N | limit 上限 20 |
| `read_file` | 受限读文件 | **路径白名单**，`..` 穿越直接拒 |
| `get_current_time` | 服务器时间 | 用于理解告警时间窗 |
| `list_approvals` | 审批单查询 | 需 `audit:read` |

**三条红线，写死在实现里而不是靠提示词：**

1. 这 9 个工具的实现代码里**不存在任何 `exec` / `spawn` / `write` 调用**。不是"提示模型别执行"，是根本没有这个代码路径。
2. 文件读取走 `allowedReadRoots` 白名单：

```js
const resolved = path.resolve(root, rel);
if (!resolved.startsWith(root + path.sep)) throw new ToolError('路径越界');
```
   
   用 `path.resolve` 之后再比前缀，而不是检查字符串里有没有 `..`——后者能被各种编码绕过。

3. 参数做字符集白名单校验：`/^[\w.\-/:* ]{0,128}$/`。这是防注入的第二道。

**工具报错不回灌"异常"，而回灌"可用的选项"**

比如 `query_logs(web-01, source='wrong')`，返回的不是 `Error: ENOENT`，而是：

```js
{ ok: false, error: 'source 不存在：wrong', hint: 'web-01 可用 source：nginx, syslog, app' }
```

模型看到可用列表，下一轮自己就能改对。这就是"能让 Agent 自我纠正的错误信息"和"只给程序员看的堆栈"的区别。

### 4.6 脚本生成：模板化而不是让模型自由发挥

`scriptgen.js` 用 6 个模板匹配意图：

| 模板 | 匹配关键词 | 用途 |
|---|---|---|
| `diagnose-collect` | 采集 / 诊断 / 排查 / 信息收集 | 一次性收集现场信息打包 |
| `log-cleanup` | 清理 / 日志 / 删除 / 磁盘 / 空间 | 按天清理过期日志 |
| `service-restart` | 重启 / restart / 服务 / systemd | 安全重启服务 |
| `disk-usage-report` | 磁盘 / 占用 / 目录 / du | 目录占用排行 |
| `config-backup` | 备份 / backup / 配置 / 快照 | 配置打时间戳快照 |
| `health-check` | 巡检 / 检查 / health / 状态 | 常规巡检五项 |

**为什么用模板而不是直接让 LLM 生成脚本？**

因为**"默认安全"必须由结构保证，不能靠模型每次都想起来**。模板产出的骨架固定包含：

- `set -euo pipefail`
- `trap ... EXIT`（命令失败 / Ctrl-C 都会有兜底）
- `APPLY="${APPLY:-0}"` + `--apply` 开关（默认 dry-run）

如果让模型每次自由生成，你无法保证这三点每次都出现。模板化等于把安全基线**编译进了产物**。

模型仍然有用：意图识别、参数填充、异常场景补充。但骨架不交给它。

### 4.7 静态门禁：两层判定 + 注释剥离

`gateScript()` 返回 `blocked` / `needs_approval` / `auto_allowed` 三种结论。

判定顺序：

```
1. 剥离注释 → 匹配高危模式（14 条 blocked）
2. lint 中 severity=critical 的项 → 也计入 blocked
3. 若有 blocked → 立即返回，不可放行
4. lint 中 severity=high 的项 → 计入 needs_approval
5. 兜底策略：任何执行都要人点头（哪怕全只读）
```

**为什么必须剥离注释**

这是踩过的真实坑。`log-cleanup` 模板的注释里写了一句：

```bash
# 用 find -delete 而不是 rm -rf，避免误删
```

结果脚本被自己的注释判成 `blocked`，永远提交不进去。

修法是 `stripComments()`，而且是**引号感知**的——`echo "# 不是注释"` 里的 `#` 不能被当注释切掉：

```js
if (c === '#' && !inSingle && !inDouble && (i === 0 || /\s/.test(line[i - 1]))) {
  return line.slice(0, i);
}
```

**门禁和 lint 是两件事，不能混用**

| | shell-lint | gate |
|---|---|---|
| 目的 | 提示风险，帮人改好 | 决定能不能执行 |
| 结论 | 分级建议（critical/high/medium/low） | 放行 / 需审批 / 拒绝 |
| 被谁用 | 阶段 2 的 diff 修复 | 阶段 4 的提交与执行 |

如果用一个"给建议"的模块去当"做决定"的闸门，就会出现"警告了一堆但还是放行了"的情况。

> 顺带说一个本项目的真实修复：自动化视图的「静态门禁体检」按钮，早期误调了 `/api/script/lint`（阶段二的体检接口），导致对 `rm -rf /data/app` 显示"需人工审批"，而真实提交时门禁判的是 `blocked`——**体检说能过、提交却被拒**。修法是新增 `POST /api/script/gate`，与提交共用同一个 `gateScript()`，从接口层面保证结论一致。

### 4.8 审批状态机：职责分离 + 二次门禁

```
draft ──提交──> pending ──批准──> approved ──执行──> executed
                   │
                   └──驳回──> rejected

任何环节命中 blocked ──> denied（拒绝入库，从未进入审批）
```

三条硬规则写死在 `approval.js` 里：

**规则 1：高危脚本不得入库**

`gate.level === 'blocked'` 时直接 403，返回 `GATE_BLOCKED` + 具体原因。**审批也救不回来**——不存在"批一下就能过"的路径。

**规则 2：提交人不能批准自己**

```js
if (!ALLOW_SELF_APPROVAL && by && item.submitted_by === by) {
  throw Errors.forbidden('不能批准自己提交的变更');
}
```

这是变更管理的核心要求（职责分离，Separation of Duties）。如果一个人能提出又能批准，审批就是形式主义。演示时用 `ALLOW_SELF_APPROVAL=1` 可以放开，但默认关闭。

**规则 3：执行前二次门禁**

```js
// executeApproved 内部
if (item.status !== STATUS.APPROVED) throw Errors.badRequest(...);
const gate = gateScript(item.script);       // 重新跑
if (gate.level === 'blocked') throw ...;
```

防的是 TOCTOU（Time-of-Check to Time-of-Use）：审批之后到执行之前，脚本可能被改过。

**状态机是显式的**

每次流转都校验前置状态。`pending` 之外的审批单不能再被决策，`approved` 之外不能执行。没有"状态随便写"的余地——这是并发和误操作的第一道防线。

### 4.9 隔离执行：用"接口形状"防绕过

这是整个项目最需要克制的部分。

**核心设计：`execute_approved` 只接受 `approval_id`，不接受脚本文本。**

```js
// write-tools.js
{
  name: 'execute_approved',
  parameters: {
    type: 'object',
    properties: {
      approval_id: { type: 'string', description: '审批单 ID' },
      mode: { type: 'string', description: 'mock / docker / local' },
    },
    required: ['approval_id'],   // 注意：没有 script 这个字段
  },
}
```

**为什么这比"检查权限"更可靠？**

假设接口接受脚本，那么任何拥有 `exec:sandbox` 权限的人（或模型）都可以直接传一段 `rm -rf /`，然后再加个"必须有 approval_id"的参数校验——但校验逻辑可能被异常路径绕过、可能被未来某次修改漏掉。

而**接口根本不收脚本**，执行路径上就不存在"传入任意脚本直接执行"的分支。这是用类型系统/接口契约代替运行时检查，可靠性高一个量级。

同理，执行前会重新从存储里读出 `item.script`——**永远执行存储里那份，不执行调用方传来的那份**。

**三种后端**

| 模式 | 实现 | 副作用 | 用途 |
|---|---|---|---|
| `mock`（默认） | 逐行模拟，只读命令与 shell 内建回显，其余标"隔离环境拦截" | 无 | 演示、CI、默认 |
| `docker` | `--rm --network=none --memory=256m --cpus=0.5 --pids-limit=64` + 只读挂载 | 有（容器内） | 真跑脚本 |
| `local` | 受限解释器，只认 `READ_ONLY_COMMANDS` 白名单 + `SAFE_BUILTINS`，**永不调用系统 shell** | 极小 | 无 Docker 环境 |

`local` 模式需要显式 `EXEC_ALLOW_LOCAL=true` 才启用，因为"在本机执行"这个语义本身就该多一道确认。

**为什么 `local` 不调 `child_process.exec`？**

因为 `exec` 会起 shell，而 shell 有重定向、管道、命令替换、变量展开……每一样都是注入面。受限解释器是逐行 `spawn` 白名单命令，参数按数组传，不经过 shell 解析。**这样在 Windows / Linux / macOS 上行为一致，也不存在 shell 注入。**

### 4.10 RBAC：声明式授权 + 双层校验

8 个权限，4 个角色（`viewer` ⊂ `operator` ⊂ `approver`）：

```js
const VIEWER   = ['chat:read', 'tool:invoke', 'script:lint', 'audit:read'];
const OPERATOR = [...VIEWER, 'script:generate', 'approval:submit'];
const APPROVER = [...OPERATOR, 'approval:decide', 'exec:sandbox'];
```

**关键点 1：权限声明在工具定义上，不散落在 handler 里**

```js
{
  name: 'approve_change',
  requiredPermission: 'approval:decide',
  // ...
}
```

好处是：`loop.js` 可以在**给模型工具列表之前**就按角色过滤掉无权工具。模型甚至不知道有这些工具存在，从源头减少无意义的调用。

**关键点 2：Agent 内和 HTTP 层用同一套规则**

```js
// loop.js —— 模型调用时
if (def?.requiredPermission) assertCan(role, def.requiredPermission, ...);

// api.js —— 手动直连时
requirePermission(req, def.requiredPermission, `调用工具 ${name}`);
```

两处都走 `assertCan`。这样不会出现"Agent 路径拦了、手动接口没拦"的漏洞。

**关键点 3：未知角色降级为 viewer**

```js
return Object.prototype.hasOwnProperty.call(ROLES, r) ? r : 'viewer';
```

最小权限原则。传 `x-ops-role: superadmin` 不会变成管理员，而是变成一个什么都不能改的观察员。

### 4.11 审计：同步写入才能"返回即留痕"

早期版本用异步 `appendFile` + 写入队列，测试里出现了一个诡异现象：调用返回后立刻读审计文件，读不到刚写的记录。

原因是 async 写入还没 flush。修法是改成 **`appendFileSync`**：

```js
fs.appendFileSync(AUDIT_FILE, JSON.stringify(entry) + '\n', 'utf8');
```

**为什么接受同步写带来的性能损失？**

因为审计的语义是"调用返回时记录必须已经存在"。异步写会让"接口返回成功"和"审计已落盘"之间出现一个窗口，而这个窗口正是事故调查时最尴尬的地方——你无法证明发生了什么。

在低 QPS 的运维场景下，一次几毫秒的同步写完全可以接受。如果真到了高并发，正确做法是本地顺序写 + 异步批量投递到集中日志系统，而不是"先返回再写"。

### 4.12 结构化错误：让前端能决定"要不要给重试按钮"

统一的 `AppError`：

```js
{ code: 'TOOL_TIMEOUT', httpStatus: 504, retryable: true, hint: '该工具响应超时，可稍后重试或缩小查询范围' }
```

HTTP 响应统一为 `{error, code, retryable, hint}`。

**为什么要 `retryable` 这个字段？**

因为不同错误该有不同的 UI 处理：

- 参数错（400）→ 重试没用，应该高亮表单
- 权限不足（403）→ 重试没用，应该提示换身份
- 门禁拒绝（403 `GATE_BLOCKED`）→ 重试没用，应该展示具体原因让人改脚本
- 模型不可用（502）→ 可以重试
- 工具超时（504）→ 可以重试，但建议缩小范围

如果所有错误都只给一个字符串，前端只能一律弹 toast，用户不知道下一步该干什么。

### 4.13 演示模式：不是假输出，是同一套链路的另一个推理后端

没有 API Key 时，`mock.js` 接管"推理"。它不是返回固定文本，而是**按真实模型的交互协议工作**：

```
第 1 轮：识别意图 → 返回 tool_calls（真的去执行）
第 2 轮：读取真实的工具返回 → 按证据拼装六段式报告 → 流式输出
```

所以 SSE 流式、多轮编排、工具回灌、Markdown 渲染、审计留痕——**整条链路都是真的**，只有"推理"这一步由规则引擎代替。

内置 5 个故障场景，每个都有完整的证据链设计：

| 场景 | 核心证据 | 想教的东西 |
|---|---|---|
| 磁盘写满 | disk 96% + inode 98% + `No space left on device` | 别只看 disk，inode 也会满 |
| Java OOM | 堆内存曲线 + `OutOfMemoryError` + 重启次数 5 | OOM Killer 会反复杀，症状是"服务自己重启" |
| 慢查询暴涨 | `slow_query` + `Lock_time` 4.99s + iowait 41.7% | 慢查询背后可能是锁等待 + IO 瓶颈叠加 |
| Redis 下线 | 日志 `User requested shutdown` + Sentinel 无法切换 | 主节点被主动关，从节点不可用 → 切换失败 |
| 网关 502 | gw-05 upstream timeout 187/min，但 app-02 同期在 OOM 重启 | **网关是受害者，只查网关找不到根因** |

最后一个场景最能体现价值：它故意构造了"症状在主机上、根因在别处"的陷阱。如果 Agent 只看网关的指标就下结论，答案是错的。

**为什么模拟数据要用种子化伪随机生成？**

`gen-fixtures.mjs` 用固定种子生成，保证每次查询结果一致。否则模型会看到"上一轮磁盘 96%、这一轮 93%"，然后开始胡乱归因——**证据不稳定会导致推理不稳定**。

## 五、关键设计决策与取舍

这一节是文档里最"值钱"的部分：为什么这么做，不这么做会怎样。

### 决策 1：执行接口只收 `approval_id`，不收脚本

| | |
|---|---|
| **选择** | `execute_approved({approval_id})`，接口里没有 `script` 字段 |
| **替代方案** | `execute_script({script, approval_id})`，靠"必须带有效 approval_id"来校验 |
| **为什么选这个** | 前者让"传任意脚本执行"在**类型层面就不可能**；后者依赖运行时检查，而检查逻辑可能被异常路径绕过、被未来修改漏掉 |
| **代价** | 想临时跑个脚本必须先走提交流程，灵活性降低 |
| **结论** | 在"执行生产变更"这个场景里，安全性优先于灵活性。要灵活可以加沙箱调试功能，但不该和执行审批流共用入口 |

### 决策 2：门禁 `blocked` 不可通过审批放行

| | |
|---|---|
| **选择** | 命中 14 条高危模式，直接拒绝且没有 override |
| **替代方案** | 高危也能提交，但要求双人审批 + 强提示 |
| **为什么选这个** | `rm -rf /`、`mkfs`、`DROP TABLE` 这类操作的期望收益几乎为零，而误操作的代价是灾难性的。给它们留 override 通道，等于把"人为失误"变成"系统性风险" |
| **代价** | 真实场景里偶尔确实需要删库，此时只能绕开系统手工操作（但那样也就没有审计了） |
| **更好的做法** | 高危操作走独立的、更重的变更流程（比如 DBA 双人复核 + 备份验证），而不是在通用工具里开个口子 |

### 决策 3：脚本用模板生成，而不是让 LLM 自由写

| | |
|---|---|
| **选择** | 6 个模板 + 参数填充，骨架固定 |
| **替代方案** | 直接把意图给 LLM，让它写完整脚本 |
| **为什么选这个** | `set -euo pipefail` / `trap` / 默认 dry-run 这三条安全基线，靠"每次祈祷模型记得"是不可靠的。写进模板等于编译进产物 |
| **代价** | 覆盖不到模板之外的场景，需要人工补充 |
| **怎么补救** | 允许用户在编辑器里改；改完仍然过门禁；门禁会指出新引入的风险 |

### 决策 4：注释剥离后才做风险匹配

| | |
|---|---|
| **选择** | `stripComments()` 引号感知剥离，再跑正则 |
| **替代方案** | 直接对全文匹配 |
| **为什么选这个** | 注释里写"不要用 rm -rf"会导致脚本被自己判死。这种误报在真实系统里极其常见，而误报的后果是**用户开始不信任门禁，进而找办法绕过**——这比漏报更危险 |
| **代价** | 理论上存在"把危险命令藏在注释里"的绕过，但注释本身不执行，所以不构成实际风险 |

### 决策 5：自己管会话历史，不用 `previous_response_id`

| | |
|---|---|
| **选择** | 客户端维护 `messages`，`responseId` 只作为可选透传 |
| **替代方案** | 全部交给 Responses API 服务端托管 |
| **为什么选这个** | 可审计（能落盘重放）、可移植（换服务商不影响）、可控（能裁剪防费用失控） |
| **代价** | 要多写裁剪逻辑，且要处理 tool 消息不能孤立的约束 |
| **什么时候该反过来选** | 如果只是做 Demo 或对成本不敏感，服务端托管更省事。生产系统里"审计"这个需求通常会把天平压向自管 |

### 决策 6：审计同步写

| | |
|---|---|
| **选择** | `appendFileSync` |
| **替代方案** | 异步队列批量落盘（性能更好） |
| **为什么选这个** | 审计的语义是"接口返回时记录已在"；异步写会留下一个窗口，而窗口期正是事故调查最需要证据的地方 |
| **代价** | 每次调用多几毫秒 IO |
| **生产化方向** | 本地顺序写（保证返回即落盘）+ 异步投递到集中日志（ELK / Loki），两者不矛盾 |

### 决策 7：前端置灰 + 服务端硬校验，两层都要

| | |
|---|---|
| **选择** | 前端按权限禁用按钮，服务端 `requirePermission` / `assertCan` 再校验一次 |
| **替代方案** | 只做前端隐藏（少写代码） |
| **为什么选这个** | 前端隐藏只是体验优化；任何人打开 devtools 改一下 `disabled` 属性就能点。**真正的安全边界只能在服务端** |
| **代价** | 两处逻辑要保持同步（用"工具定义上声明权限"来收敛，避免发散） |

## 六、一次完整请求的生命周期

以"提交一个变更并执行"为例，把路径串起来：

```
[浏览器]
  用户在自动化视图填入意图，点「生成草稿」
  ↓ POST /api/script/generate  { intent, target_host }
[路由层]
  requirePermission(req, 'script:generate')   ← operator 及以上才过
  ↓
[scriptgen]
  pickTemplate(intent) → 'log-cleanup'
  generateScript() → 52 行带骨架脚本
  gateScript() → { level: 'needs_approval', reasons: [...], counts: {...} }
  ↓ 返回 { script, gate, template }
[浏览器]
  渲染脚本到编辑器，门禁结论显示"需人工审批"
  用户点「提交审批」
  ↓ POST /api/approvals  { script, intent, target_host }
[路由层]
  requirePermission(req, 'approval:submit')
  gateScript(script)                    ← 第一道门禁
  blocked? → 403 GATE_BLOCKED（不入库）
  ↓
[approval]
  submitApproval() → id: AP-20261016-xxxx, status: pending
  写 data/approvals.json
  record({ type: 'approval_submit', actor, role, ... })
  ↓ 返回 { id, status: 'pending' }


[浏览器] 换个身份（release-manager@demo, approver）
  ↓ POST /api/approvals/AP-xxx/decision  { decision: 'approve' }
[路由层]
  requirePermission(req, 'approval:decide')
  ↓
[approval]
  decideApproval():
    - 状态必须是 pending
    - submitted_by (duty-lead@demo) ≠ by (release-manager@demo)   ← 职责分离
    - 有 approval:decide 权限
  → status: approved, decided_by, decided_at
  record({ type: 'approval_decision', decision: 'approve' })


[浏览器]
  ↓ POST /api/approvals/AP-xxx/execute  { mode: 'mock' }
[路由层]
  requirePermission(req, 'exec:sandbox')
  ↓
[executor]
  - 读存储里的 item.script（不读调用方传的）
  - 校验 status === 'approved'
  - gateScript(item.script) 重新跑一遍           ← 第二道门禁（防 TOCTOU）
  - blocked? → 拒绝
  - executeScript({ mode: 'mock' }) → 逐行模拟
  ↓
[approval]
  markExecuted() → status: executed, execution: { exitCode, stdout, durationMs, simulated }
  record({ type: 'exec_finished', actor, role, ok, ms })
  ↓ 返回执行结果
[浏览器]
  展示 stdout / stderr / 退出码，标注「模拟执行」
```

**四道卡口，任何一道失败都会中断，且每一道都记审计**：

```
权限 → 门禁 → 职责分离 → 二次门禁 + 状态校验
```

### 7.2 执行器单测（`test/unit-exec.mjs`）

免起服务，直接测 `gateScript()` 和 `executeScript()`：

```
只读脚本        → needs_approval（仍需审批）
rm -rf 变量     → blocked（多重原因叠加）
curl | bash    → blocked（两个模式都命中）
rm -rf 绝对路径 → blocked

```

以及模拟执行的真实输出、高危拦截返回 `denied: true`。

**为什么单独拆出来**：门禁是最核心的安全逻辑，需要有"改一行就能跑"的快速回归。

### 7.3 浏览器 UI 测试：41 项（`test/browser-check.mjs`）

用 `playwright-core` 驱动真实浏览器，走完整用户路径：

- 首屏渲染（含**写操作工具不能被误标为只读**）
- 阶段 1：点击场景 → SSE 流式渲染 → 工具卡片 → Markdown 结构
- 阶段 2：载入示例 → 体检 → diff → 确认应用
- 阶段 3：工具下拉分组 → 调用 → 路径穿越在 UI 层也被拒
- 阶段 4：生成 → 门禁结论 → 提交 → 队列 → **自批按钮禁用** → 换人批准 → 执行 → stdout 面板
- 阶段 5：切 observer 后生成按钮禁用、切回恢复
- **控制台无 JS 运行时错误**

最后一条特别重要：很多前端 bug 不体现在断言里，只体现在 console 的红色报错里。

### 7.4 测试里发现的真实问题（举三个）

| 问题 | 根因 | 修法 |
|---|---|---|
| 审批后立即读审计读不到 | `appendFile` 异步未 flush | 改 `appendFileSync` |
| 测试请求返回 HTML 导致 `JSON.parse` 报 `Unexpected token '<'` | 三个 URL 少了 `/api` 前缀，落到 SPA fallback | 补全路径 |
| 门禁体检说"需审批"，提交却被拒 | UI 调了阶段二的 lint 接口而非门禁 | 新增 `/api/script/gate`，与提交共用 `gateScript()` |

## 八、已知边界与生产化差距

诚实地列出"这个 Demo 到生产还差什么"，比宣称"已完成"更专业。

| 差距 | 现状 | 生产化建议 |
|---|---|---|
| **身份认证** | 用 `x-ops-role` / `x-ops-actor` 请求头，**可伪造** | 换 SSO / OIDC / 堡垒机下发的真实身份；服务端签发会话，绝不信任客户端自称角色 |
| **执行目标** | `mock` 模拟 / `docker` 本地容器 | 接堡垒机 + 受限账号（sudo 白名单），或 K8s Job；执行前后打快照 |
| **审批持久化** | `data/approvals.json` 单文件 | 换数据库，加行级锁、版本号（乐观锁）、不可篡改存储（WORM） |
| **审计存储** | 本地 append-only JSONL | 按日切割 + 异地备份 + 投递到集中日志（ELK/Loki）+ 完整性校验（哈希链） |
| **监控数据源** | `sandbox/` 确定性模拟数据 | 换 Prometheus / Zabbix / 云监控。**只改 `tools.js` 的实现，不动定义** |
| **并发** | 单进程内存会话 | 多实例需外置会话（Redis）+ 审批单加锁 |
| **安全隔离强度** | `docker` 有网络隔离与资源限额 | 更强的需要 gVisor / Firecracker；并明确"隔离 ≠ 防逃逸" |
| **模型成本控制** | 轮次上限 + 历史裁剪 | 加 token 预算、按用户配额、缓存常见取证结果 |

**关于"私有化部署"的表述边界（重要）**

本项目部署的是**执行环境、工具和数据的自托管**，模型本身始终通过 API 调用，**没有把模型权重下载到本地**。

这两件事在技术汇报和简历里必须分开写：

- ✅ 可以说：Agent 编排层、工具层、执行环境、数据与审计都在自有机器上
- ❌ 不能说：私有化部署了大模型
- ❌ 不能说：了解 Codex 内部大模型原理（公开的 Agent 机制、调用流程、工具编排可以学；未公开的内部实现无法通过本项目掌握）
- ⚠️ 说"隔离执行"时要讲清程度：默认是 `mock` 模拟执行（零副作用），`docker` 模式才有真正的网络隔离与资源限额

## 附：一句话总结

> 这个系统的价值不在于"用 AI 分析日志"，而在于**它把 AI 放到了一个有边界的位置上**：
> 让模型负责理解和表达，让代码负责取证和约束，让人负责批准和担责。
> 四道卡口（权限 → 门禁 → 职责分离 → 二次门禁）加上全程审计，
> 使得"AI 参与生产变更"这件事从"不敢用"变成了"可以谈"。
