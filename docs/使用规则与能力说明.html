AI 运维故障分析助手 · 使用规则与能力说明

这份文档回答两个问题：它究竟能做什么、用的时候必须遵守哪些规则。

它不讨论架构取舍——那部分在 技术设计文档.md 里。本文所有结论均对照源码核对过，

涉及"文档说法与代码实际不一致"的地方会单独标注。

一、它是什么

一个本地运行的运维 Agent，把一次运维处置拆成五个可审计的环节：

日志告警分析 → Shell 脚本校错 → 只读取证 → 生成脚本 → 人工审批 → 隔离执行
   （理解现场）   （改别人的脚本）  （查证据）  （写新脚本）  （别人点头）  （跑起来）

核心特征是全程人工确认 + 全程审计留痕：AI 不会自己动手改任何东西，它只能产出"建议"， 每一步落地动作都需要一个人手持相应权限按下确认。

它不是

常见误解实际情况
一个会自动登录服务器处置故障的机器人默认 EXEC_MODE=mock，零副作用；真实执行需显式切换模式
一个接入了真实监控的平台数据来自 sandbox/inventory.json 的确定性模拟数据，换真实监控需改工具实现
一个私有化部署的大模型模型始终走 OpenAI 兼容 API，本地只部署了执行环境、工具和数据
一个既有身份认证的系统角色靠请求头 x-ops-role 自报，任何人都能伪造，生产必须替换

二、它究竟能做什么

能力 1 · 故障分析（阶段 1）

触发方式：在「故障分析」标签页输入日志片段/告警文本，或直接点内置场景。

输出是固定六段结构，不允许自由发挥：

  1. 结论摘要
  2. 证据链
  3. 可能原因（按可能性排序，每条带概率与判据）
  4. 排查步骤
  5. 修复建议（分"短期止血 / 长期根治"）
  6. 还需补充的信息

硬性规则：每条结论必须引用工具返回的指标数值或日志原文。 文档里的表述是"不允许无依据输出"——这是提示词层面的约束，配合工具取证来保证。

内置 5 个演示场景：磁盘写满（含 inode）、JVM OOM、慢查询暴涨、Redis 下线、网关 502。 选场景后一键填入，无需自己编日志。

网关 502 这个场景是设计得最巧的一个：结论明确说"网关是受害者，只在 gw-05 上排查找不到根因"，

引导追到上游 app-02 的 OOM 重启周期。它演示的是因果链推断，不是单点查指标。

能力 2 · 脚本校错（阶段 2）

输入：任意 Shell 脚本（或载入 samples/risky-deploy.sh）。

三段式流程，顺序不可颠倒：

步骤谁来做特点
① 本地静态体检server/lib/shell-lint.js确定性规则，毫秒级，零成本、零延迟、零幻觉
② AI 语义补充模型按强约束 JSON Schema 返回，不自由行文
③ 人工确认你每条修复先出 diff，点了"确认应用"才落地

AI 必须返回的结构：

{ "summary": "...", "overall_risk": "high",
  "issues": [ { "severity": "high", "line": 12, "risk": "...", "suggestion": "...", "patch": {} } ] }

补丁只有两种形态，且都是精确定位：

  • { type: 'replace', find, replace } —— 逐字替换，find 必须是原文子串
  • { type: 'insert', anchor, position, text } —— 在锚点行前/后插入

关键规则：原文件永远不会被直接改写。 前端逐字定位替换生成"修改后文本"， 先渲染 diff 给你看，你不点确认，编辑器内容一个字符都不变。 这是为了堵住"让 AI 自由改写整份文件"导致的大面积误改。

体检规则清单（20 条，按严重度排序）

严重度规则典型风险
criticalrm -rf 作用于未加引号的变量变量为空时退化成 rm -rf /*
criticalcurl | bash / wget | sh执行未经审计的远端内容，无法校验版本
criticalchpasswd 批量改密码时机不对会把自己锁在系统外，不可回滚
high缺少 set -euo pipefailcd 失败后继续 rm，删到错误目录
highrm -rf 用变量但缺前置校验值不合预期时同样不可逆
high对根路径/通配路径强制删除系统级损坏
high明文机密写进变量（pass/pwd/secret/token/key）随脚本进 Git、镜像、CI 日志
high数据库密码走命令行参数ps -ef 可见，进 history 与审计日志
highkill -9 / killall / pkill -9来不及优雅退出，丢数据、连接中断
highecho 打印凭据变量明文进终端与日志文件
medium缺少 shebang可能被 dash/sh 解释，行为不一致
medium|| true 吞掉错误迁移失败被标记成功，上线半成品
mediumcd 之后未校验后续相对路径操作全错位
medium命令参数中的变量未加引号空格分词、- 开头被当选项
medium缺少备份或回滚入口新版本不可用时无法分钟级回滚
lowps aux | grep 缺 grep -v grep匹配到 grep 自身，作用于错误 PID
low用固定 sleep 等就绪高负载时不够，空闲时白等
low用 $? 判断上一条命令中间插一条 echo 就覆盖了
low缺少 trap 清理中断后残留临时文件、锁、挂载点
low开启 set -x追踪输出会展开变量，泄露凭据

其中 7 条规则附带可机读的 patch（shebang、严格模式、rm -rf、curl|bash、明文凭据、cd 校验、sleep 轮询、备份入口）， 其余只给建议不自动改——因为改法依赖具体上下文，硬套反而更危险。

能力 3 · 只读取证（阶段 3）

8 个只读工具（另有 list_approvals 归在写工具组，权限却是只读的 audit:read，合计 13 个工具）：

工具用途
list_hosts列出受管主机（角色、IP、环境、规格），排障第一步
query_metrics查时序指标（CPU/内存/IO/慢查询等）
get_alerts当前未恢复告警，可按主机与严重级别过滤
query_logs按主机/关键字/时间窗查日志
check_services关键服务状态（systemctl status 的只读视图）
top_processes进程资源占用 TOP N
read_file读文件（走路径白名单）
get_current_time服务器当前时间，用于对齐告警与日志窗口
list_approvals列审批单（权限 audit:read，所有角色可用）

4 个写操作工具：

工具所需权限
generate_scriptscript:generate
submit_for_approvalapproval:submit
approve_changeapproval:decide
execute_approvedexec:sandbox

关键行为：工具报错不终止会话。 错误文本会作为工具结果回灌给模型， 模型看到"可用 source 列表"后自己换路子重试——这是真实 Agent 与"一问一答"的分水岭。 权限不足同理：把"权限不足"回灌，而不是中断。

能力 4 · 自动化运维（阶段 4）

四步，每一步都是不可跳过的卡口：

意图 → ①生成草稿 → ②静态门禁 → ③提交审批 → ④隔离执行
       scriptgen      gate         approval      executor
       ↑安全骨架    ↑高危直接拒    ↑职责分离     ↑只认 approval_id

① 生成：6 个内置模板

日志清理 / 重启服务 / 磁盘巡检 / 配置备份 / 健康检查 / 诊断采集，按意图关键词匹配。

生成的脚本自带三件套，不是裸脚本：

  • set -euo pipefail
  • trap ... EXIT 清理与退出码捕获
  • 默认 dry-run —— 必须显式传 --apply 才真正落地

② 门禁：两级判定

blocked（直接拒绝入库，返回 403 GATE_BLOCKED，审批也救不回来）—— 14 条：

rm -rf · mkfs · dd if= · chpasswd · shutdown/reboot/poweroff/halt · init/telinit 0|6 · 管道执行 Shell（| sh | bash） · curl|wget 下载执行 · chmod/chown 777 · 直接写块设备（> /dev/sda） · DROP DATABASE/TABLE · 无 WHERE 的 DELETE FROM · userdel/groupdel · systemctl stop/disable/mask

needs_approval（可入库，但必须人工批准）—— 4 条：

find -delete · systemctl restart · kill/killall/pkill · cp -f / mv -f

其余脚本一律 needs_approval，包括纯只读脚本——策略就是"任何执行都要人点头"， 不设"看起来无害所以放行"的例外。

门禁匹配前会先做引号感知的注释剥离。这一步修掉了一个真实误判：日志清理模板的注释里

写着"用 find -delete 而不是 rm -rf"，结果脚本被自己的注释判死。

注释剥离要感知引号，否则 echo "# not a comment" 会被截断。

③ 审批：状态机 + 职责分离

draft → pending → approved / rejected → executed
                ↘ denied（门禁处被拒，从未入库）

提交人不能批准自己提交的变更，HTTP 层与工具层双重拦截。 演示时可设 ALLOW_SELF_APPROVAL=1 放开，默认关闭。

④ 执行：三种模式

模式行为适用
mock（默认）逐行模拟输出，标注 simulated: true，零副作用演示、CI
dockerdocker run --rm --network=none --memory=256m --cpus=0.5 --pids-limit=64，工作区只读挂载真要跑
local受限解释器，只认 21 个只读命令 + 9 个内建，永不调用系统 shell无 Docker

本节最重要的一条设计：

execute_approved 只接受 approval_id，不接受脚本文本。

执行路径上没有任何"传入任意脚本直接执行"的分支——接口形状本身就是防绕过的。

即使有人拿到 exec:sandbox 权限，能执行的也只是"别人提交、别人批准过、且通过门禁"的那一份。

执行前还会重跑一遍门禁并重新校验状态为 approved。

能力 5 · 权限与审计（阶段 5）

4 个角色，8 个权限点：

角色chat:readtool:invokescript:lintscript:generateapproval:submitapproval:decideexec:sandboxaudit:read
viewer 观察员✓✓✓————✓
operator 运维执行✓✓✓✓✓——✓
approver 变更审批人✓✓✓✓✓✓✓✓
admin 管理员✓✓✓✓✓✓✓✓

权限规则：

  • 每个工具在自己定义里声明 requiredPermission，不是散落在 handler 里的 if
  • Agent 循环按角色过滤可用工具——没权限的工具根本不会出现在给模型的工具列表里
  • 未知角色一律降级为 viewer（最小权限原则）
  • 真正的边界在服务端：前端置灰只是体验，直接发 HTTP 请求一样被拒 403

⚠️ 文档与实现不一致（实测发现）：README 写 admin 拥有"全部权限"，但 rbac.js 里

admin: { permissions: [...APPROVER] }——与 approver 完全相同的权限集，只是标签不同。

也就是说当前代码里不存在"只有 admin 能做而 approver 不能做"的操作。

这不影响使用，但如果要演示"管理员比审批人更高一级"，需要自己补权限点。

审计：

  • append-only JSONL，落 data/audit.log，同步写入（返回时已落盘，可被立即读取验证）
  • 每条含 ts / type / actor / role / 入参 / 结果 / 耗时
  • 覆盖 6 类事件：chat / tool_call / tool_denied / approval_submit / approval_decision / exec_finished
  • 界面审计抽屉可按类型过滤，GET /api/audit/export 导出 JSONL
  • 可直接接 SIEM

三、使用规则

规则集 A · 环境与启动

项目要求
Node.js>= 18.17.0（package.json 声明）
运行时依赖只有 express，没有其他运行时依赖
端口默认 8787，改 PORT=8800 npm start
绑定地址默认 127.0.0.1，生产必须改并加反代认证
无 Key 运行自动进入演示模式，界面与流程完整可跑
npm install
npm start            # 打开 http://127.0.0.1:8787
cp .env.example .env # 要接真模型时填 Key

演示模式下 Agent 依然真实执行"规划工具 → 取证 → 回灌 → 成文"的多轮循环， 只是推理换成本地规则引擎。链路、事件流、界面与真实模型一致——所以它可被当作可靠的演示。

规则集 B · 五个标签页各自的用法

1）故障分析

  • ✅ 可以直接点场景，也可以用自己的一段真实日志
  • ✅ 允许 AI 调只读工具补证据
  • ❌ 不要把生产环境的真实口令、内网地址贴进去——内容会进会话历史与审计日志
  • ⚠️ 结论里的"可能性排序"是模型判断，不是统计概率，不可当故障概率用

2）脚本校错

  • ✅ 先跑本地体检（毫秒级），再看 AI 补充
  • ✅ 每条修改必须看过 diff 再确认
  • ❌ 不要点"全部应用"跳过逐条审阅——patch 是逐字替换，上下文不匹配时不会报错，只会静默不生效
  • ⚠️ 体检规则是模式匹配，能抓典型反模式，但抓不到"逻辑正确但业务上行不通"

3）工具沙箱

  • ✅ 可以手动调任一只读工具验证返回结构
  • ✅ 可以用来演示路径穿越被拒（试 ../../etc/passwd）
  • ❌ 没有任何写操作工具可供手动调用——执行只能由审批单驱动

4）自动化运维

  • ✅ 选模板 → 生成 → 看门禁结论 → 提交 → 换个身份批准 → 执行
  • ❌ 不能自己批自己（默认策略）
  • ❌ 门禁 blocked 的脚本不能被审批放行，这是设计而非缺陷
  • ⚠️ 生成的脚本默认 dry-run，真正生效要加 --apply

5）权限与审计

  • ✅ 顶栏可切身份，按钮即时置灰/恢复
  • ✅ 审计抽屉按类型过滤、导出 JSONL
  • ❌ 演示用身份切换是请求头，生产绝不能这样上

规则集 C · 安全红线（写死在代码里，不靠提示词约束）

这七条是"规则"里最硬的部分——它们不是靠模型自觉，而是代码结构上就没有那条路：

  1. 只读工具服务端不存在任何 exec/spawn/write 分支——不是"禁止调用"，是"没有这个函数"
  2. read_file / query_logs 走路径白名单（sandbox/ 与 samples/），任何 .. 穿越直接拒绝
  3. 工具结果统一截断，防止单次大结果撑爆模型上下文
  4. 每次工具调用写 append-only 审计日志
  5. execute_approved 只收 approval_id，不收脚本文本
  6. 执行前重跑门禁，并重新校验状态为 approved
  7. 未知角色降级 viewer

规则集 D · 执行模式的三条使用纪律

模式纪律
mock默认就用它。看到 simulated: true 就知道什么都没发生
docker先确认 Docker daemon 不与生产共享命名空间；镜像是 alpine:3.19，脚本里的 bash 语法可能不可用
local需要双重开关：EXEC_MODE=local 且 EXEC_ALLOW_LOCAL=true，缺一个都拒绝

local 模式的真实能力边界（重要，容易被误读）：

它不是一个真 bash。它逐行执行，且：

  • 只认 21 个只读命令：echo ls cat date pwd df free uptime id uname head tail wc du ps whoami hostname stat which env grep find
  • 9 个 shell 内建只标记"已识别、无副作用"，不真正执行
  • 控制结构（if/for/while/case/function/trap）直接跳过
  • 变量赋值直接跳过
  • 参数含 ; & | $ < > ( ) { } [ ] ! * ?` 任一元字符 → 整行拒绝
  • 文件访问限定在 sandbox/workspace/ 内，越界报错

所以 local 模式的用途是演示"隔离到什么程度"，不是"跑真实运维脚本"。

四、能力边界：它做不到什么

写清这一节，比写它能做什么更重要。

1. 默认不真执行

EXEC_MODE=mock 时脚本被逐行"演"一遍，输出带 simulated: true。 任何把 mock 输出当成"已在服务器验证"的说法都是错的。

2. docker 才有真隔离，local 没有

docker 模式有真正的 --network=none + 资源限额 + 只读挂载。 local 是"受限解释器"——安全来自"只认白名单命令"，不是来自"验证过的沙箱逃逸防护"。 这两句话在对外表述时必须分清。

3. 数据是模拟的

sandbox/inventory.json 由 node sandbox/gen-fixtures.mjs 种子化生成， 保证多次查询结果一致（否则模型会因前后证据矛盾而胡乱归因）。

换成真实数据源只改实现、不动定义：

// 现在：读 sandbox/inventory.json
// Prometheus: GET /api/v1/query_range
// Zabbix:     zabbix.history.get
// 阿里云监控: DescribeMetricList

4. 身份是自报的

x-ops-actor / x-ops-role 请求头由前端自由设置。任何人改一下请求头就是 admin。 生产必须换成 SSO / OIDC / 堡垒机下发的真实身份。

5. 审批单不是不可篡改的

落 data/approvals.json 单文件。生产应换数据库并加行级锁与不可篡改存储。

6. 模型本身没被私有化

本地部署的是执行环境、工具、数据；模型始终通过 API 调用。 "私有化部署执行环境" ≠ "私有化部署大模型"，这两句混着说会被直接判定为夸大。

六、三条典型路径

路径 A · 排一个故障（只读，零风险）

故障分析页 → 贴日志 → AI 调 list_hosts 确认主机
        → query_metrics / get_alerts / query_logs 取证
        → 输出六段结论 → 你照着排查步骤处理

全过程不产生任何写操作。角色用 viewer 就够。

路径 B · 改一份别人的脚本

脚本校错页 → 载入脚本 → 本地体检出 20 条 → AI 补充语义问题
        → 逐条看 diff → 逐条确认应用 → 人工复核 → 提交仓库

角色 viewer（script:lint 已包含）。

路径 C · 跑一次变更（完整四步）

自动化运维页 → 选模板 → 生成（自带 dry-run + trap + strict）
  → 门禁体检（blocked 就到此为止）
  → 提交审批（operator）

八、一页纸总结

能做什么：分析故障给结论、检查脚本给补丁、只读取证、生成带安全骨架的脚本、 走完"审批→隔离执行"、按角色控制权限、全程留审计。五阶段全部落地，有 74 + 41 + 单元三层测试覆盖。

使用规则的本质是三句话：

  1. AI 只产出建议，落地必须人确认 —— 改脚本要逐条点确认，执行要别人批准。
  2. 危险动作在代码层就被拦住，不依赖提示词 —— 14 条直接拒、4 条需审批、接口不收裸脚本。
  3. 默认什么都不真做 —— mock 零副作用，真实执行必须显式切换模式并满足前置开关。

必须记住的边界：数据是模拟的、身份是自报的、默认是模拟执行的、模型是 API 调用的。 这四条决定了它现在是一个可完整演示与验证流程正确性的工程原型， 接真实生产还需替换数据源、认证、审批存储与执行后端。
